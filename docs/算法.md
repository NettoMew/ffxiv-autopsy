# 算法

从一条报告链接到表格里那个分数，中间每一步的定义。所有公式都可以照着复算，
文末给了一个能对上实际输出的完整算例。

本文沿用推导时的写法，与输出里的叫法对应关系是：阶段即 **P**，分位即**百分位**，
线性即**区间分**，计分阶段即**算分 P**，一次 pull 即**一把**。

## 总览

```
报告链接
   │
   ├─ v1 接口 ──→ 战斗列表 ──→ ① 阶段窗口切分
   │                              │
   │                              ├─ 每个完整窗口一次表格请求
   │                              ↓
   │                          ② 每秒数值（每把每阶段每人一个）
   │                              │
   │                              ↓
   │                          ④ 多把聚成代表值
   │                              │
   └─ 统计页 ──→ ③ 官方分位曲线 ──┤
                                  ↓
                              ⑤ 分位 / 线性 / 相对中位
                                  │
                                  ↓
                              ⑥ 按时长加权的玩家总分
```

两个数据源用同一套英文职业标识（`Dragoon`、`Sage`……）对齐，这是它们唯一的连接点。

## ⓪ 整场窗口

通关的那把额外切一个整场窗口，编号 0，与统计页的 `phase=0` 对应——已核对过，
统计页 phase 0 给的就是整场分布，与从排行榜全量算出来的整场分布误差在 1% 以内。

整场**不参与 ⑥ 的加权总分**：整场本来就是各 P 之和，算进去等于把同一份成绩数了两遍。
团灭的那些把没有整场窗口。

## ① 阶段窗口切分

**输入**：`/v1/report/fights/{code}` 返回的每一把战斗，其中 `phases` 是阶段转折点列表
`[{id, startTime}, ...]`，`end_time` 是战斗结束时刻，`kill` 表示是否通关。

**输出**：一组时间窗口。对第 `i` 个转折点：

```
start_i    = phases[i].startTime
end_i      = phases[i+1].startTime   若存在，否则 fight.end_time
duration_i = end_i − start_i
```

**两条筛选规则**，都不是可选项：

```
若 duration_i ≤ 0        → 丢弃这个阶段
complete_i = (i 不是最后一个) 或 kill
```

第一条处理从中途阶段开打的 pull。这类 pull 里被跳过的阶段，其转折点与下一个阶段同刻，
长度为 0，在报告中不代表任何战斗时间。

第二条是整套算法里最关键的一条。官方分布取自通关记录，每个阶段都是完整打完的；
一把在 P5 打了 66 秒就团灭，这 66 秒里的数值和完整的 P5 不是同一个量。
`complete = false` 的窗口**只展示、不计分**，也不会去请求它的数据。

阶段编号 `id` 与统计页的 `phase` 参数、报告给出的阶段名单三者共用同一套编号，
名称取 `names[id − 1]`。

**实现**：`src/domain/phases.ts`

## ② 窗口内的每秒数值

**输入**：`/v1/report/tables/{view}/{code}?start&end`，其中 `view` 由口径决定。

| 口径 | 表格视图 | 取用字段 | 统计页 metric | 统计页 dpstype |
| --- | --- | --- | --- | --- |
| `rdps` | `damage-done` | `totalRDPS` | `dps` | `rdps` |
| `adps` | `damage-done` | `total` | `dps` | `pdps` |
| `ndps` | `damage-done` | `totalNDPS` | `dps` | `ndps` |
| `cdps` | `damage-done` | `totalCDPS` | `dps` | `cdps` |
| `hps` | `healing` | `total` | `hps` | — |

**公式**：

```
每秒数值 = 取用字段 / (combatTime / 1000)
```

`combatTime` 取自该次表格响应，缺失时退回 `totalTime`，再缺失时退回窗口长度。

**除数必须是 `combatTime` 而不是窗口长度**。这是逆向出来的，不是猜的：用它复算国服龙骑
榜首那次通关，得 `7972.33690838507`，官方公布值 `7972.3369083851`，差在 1e-11 量级；
若改用窗口长度会系统性偏高约 0.44%。`src/domain/domain.test.ts` 用真实数值把这条锁住了。

**参与者过滤**：类型为 `LimitBreak`、`NPC`、`Pet`、`Boss` 的条目一律剔除。宠物伤害由接口
自身并入主人，不需要额外处理。`boss` 编号为 0 的杂兵段落在读取战斗列表时就被排除。

一次请求覆盖整支队伍，所以请求数等于「完整阶段窗口数」，与人数无关。

**实现**：`src/domain/metrics.ts`、`src/net/fflogs.ts`

## ③ 官方分位曲线

**来源**：副本统计页的表格接口。阶段编码在 partition 上，与页面自身的做法一致：

```
partition = 版本分区 + 阶段编号 × 1000
```

版本分区、难度、队伍规模都从统计页自身读出（`var defaultPartition = …`），不写死在代码里。
阶段编号 0 表示整场。

**四次请求凑出九个锚点**。`dataset=1000` 那次返回的是箱线图，一次给出五个分位加两项表格数据，
各字段的含义已逐一核对：

| 页面上的字段 | 实际含义 |
| --- | --- |
| `q1` | p25 |
| `median` | p50 |
| `q3`（同时是表格主列） | p75 |
| `high`（上须） | p95 |
| 散点 `y` | p99 |
| 表格「最高」列 | 真最大值，即 p100 |
| 表格「记录数」列 | 官方样本量 |
| `low`（下须） | 不采用，无法确证对应哪个分位 |

另外三次分别取 `dataset=0`（真最小值，p0）、`dataset=10`、`dataset=90`。合起来：

```
锚点 = { p0, p10, p25, p50, p75, p90, p95, p99, p100 }
```

**单调化**：九个值来自四次不同请求，极少数情况下会出现毫厘倒挂，逐点取
`value_k = max(value_k, value_{k−1})` 强制不减，保证插值不会出现负斜率。

**取样窗口**是页面的 `sample` 参数，单位是天，**各副本提供的档位不一样**，
必须从页面自己读（`var defaultSample` 与 `setSample(n, this)` 的那组链接）：
幻想龙诗给 14/42/84（2 周到 12 周），光暗未来只给 1/7/14（一天到两周）。
写死一个它不提供的天数，返回的是一张空表而不是报错。默认用页面自己的默认档。

窗口之外的历史记录不在分布里，这也是为什么一次十九周前的通关可以高于当前的「最高值」。

**缓存**：基准按（副本，boss，口径，分区，窗口）落盘，按阶段惰性补齐，只抓当前报告
真正用得到的阶段。

**实现**：`src/net/statistics.ts`、`src/net/statistics-page.ts`

## ④ 多把聚成代表值

样本先按（玩家，职业，阶段编号）分桶。同一玩家换职业会分到不同的桶。

设某个桶里有 `n` 把的数值，升序排列为 `v_1 ≤ … ≤ v_n`：

```
aggregate = median（默认）
    n 为奇数 → 代表值 = v_(n+1)/2
    n 为偶数 → 代表值 = (v_(n/2) + v_(n/2+1)) / 2

aggregate = best
    代表值 = v_n
```

「最佳」列始终是 `v_n`，与口径无关，只展示不计分。

默认取中位数是为了衡量**稳定表现**，一把超常发挥不会把分拉上去；`--aggregate best`
衡量的是上限。

**该阶段的时长**取这一桶里各把时长的算术平均：

```
平均时长 = (Σ duration) / n
```

它同时是 ⑥ 里的加权权重。

**实现**：`src/domain/scoring.ts` 的 `buildScoreboard`

## ⑤ 三个派生值

设代表值为 `v`，官方曲线锚点为 `(q_k, x_k)`，`k = 0…8`，`q` 与 `x` 均升序。

### 样本闸门

```
reliable = 曲线存在 且 sampleSize ≥ 30
```

不满足时**分位与线性都不计算**，输出为「样本不足」。极少有队伍从第一阶段开始打，
首阶段的官方记录常常只有个位数，拿两三条记录当分布，谁都是满分。
阈值 30 定义在 `src/domain/scoring.ts` 的 `MIN_SAMPLE`。

### 分位

九个锚点之间线性插值，两端夹住：

```
v ≤ x_0        → 分位 = 0
v ≥ x_8        → 分位 = 100
否则找到 x_{k−1} < v ≤ x_k：
    ratio = (v − x_{k−1}) / (x_k − x_{k−1})        分母为 0 时取 ratio = 0
    分位  = q_{k−1} + (q_k − q_{k−1}) × ratio
```

这是主分。它不会被一个开场就阵亡的极端样本带偏——那种样本只影响 `x_0`，
而 `x_0` 到 `x_1` 之间跨了整整 10 个分位，斜率极缓。

### 线性

```
线性 = clamp( 100 × (v − x_0) / (x_8 − x_0), 0, 100 )        x_8 ≤ x_0 时取 0
```

即「在官方最低值与最高值之间的位置」，直观但受极值影响大，只作参考。

### 相对中位

```
相对中位 = v / x(p50) − 1
```

它是原始比较而非分数，因此**即使 `reliable` 为假也照常计算并展示**。

**实现**：`src/domain/baseline.ts`

## ⑥ 玩家总分

只有 `percentile` 非空的阶段（即完整打完、且官方样本足够）参与。设这些阶段为 `P`：

```
权重 w_p  = 阶段 p 的平均时长
总分      = Σ(分位_p × w_p) / Σ(w_p)
线性总分  = Σ(线性_p × w_p) / Σ(w_p)
```

按时长加权而不是简单平均，是因为 P4 只有 75 秒而 P6 有 144 秒，两者对一场战斗的
贡献本就不同。若 `Σ w_p = 0`（没有任何阶段可计分），总分为空。

**最强 / 最弱**：在参与计分的阶段里取分位的最大值与最小值，并列时取靠后的那个阶段。

**排序**：玩家按总分降序，无总分者排在最后。

**计分阶段**列显示 `已计分阶段数 / 有数据的阶段数`，分母含被样本闸门挡下的阶段。

**实现**：`src/domain/scoring.ts` 的 `weighted`、`pick`

## ⑦ 点评规则

表格给的是数字，点评负责把数字里值得开口说的部分挑出来。**每一条结论都由一个算得出来的量
支撑，并且把那个量一并写进句子**，读的人可以立刻回表格核对，不必信任这一层的判断。

四个程度：`严重`、`注意`、`观察`、`亮点`。

### 全队

| 结论 | 触发条件 |
| --- | --- |
| 全队最弱阶段 | 各阶段按参与者分位的算术平均排序，取最低的那个；至少要有 2 人参与该阶段 |
| 升级为「严重」 | 该阶段**所有**参与者都低于官方中位，这种一致性更像打法问题而非个人发挥 |
| 阶段不均衡 | 最强阶段与最弱阶段的平均分位相差 ≥ 25 |
| 最常团灭处 | 按未计分阶段统计团灭次数，取最多的；并列时一并列出；次数 < 2 不提 |

### 单个玩家

**最薄弱阶段**这一条永远输出，它是整份点评的主干。按严重程度分档：

```
代表值 < 官方最低值(p0)   → 严重   「同职业同阶段没有任何一条公开记录比这更低」
分位 < 10                 → 严重   「落在同职业后 10%」
分位 < 25                 → 注意   「落在同职业后 25%」
其余                      → 观察   只陈述分位与相对中位
```

然后按严重程度补一条，最多两条：

| 结论 | 触发条件 |
| --- | --- |
| 阶段内波动（注意） | 某阶段 pull 数 ≥ 3 且 `(最好 − 最差) / 代表值 > 25%`，取波动最大的那个阶段 |
| 阶段落差（观察） | 最强与最弱分位相差 ≥ 25 |
| 突出表现（亮点） | 最强阶段分位 ≥ 90 |

两处刻意的克制：

**波动阈值定在 25% 而不是更低。** 进度期本来就把把不同，差个一两成是常态，说出来只是噪音。
这一条的句子里会附带说明「计分取的是中位数，个别失手的 pull 不会拉低分数」，避免被误读成扣分项。

**「输出能力本身没问题」只在最强阶段分位 ≥ 60 时才说。** 否则落差再大，也只是全程都不理想，
不该给出一句安慰性的结论。

**实现**：`src/domain/insights.ts`

## 全程被排除的东西

| 对象 | 在哪一步排除 | 原因 |
| --- | --- | --- |
| `boss = 0` 的段落 | 读取战斗列表 | 杂兵，不是 boss 战 |
| 长度为 0 的阶段 | ① | 该 pull 跳过了这个阶段 |
| 团灭截断的末阶段 | ① | 与官方通关数据不可比 |
| `LimitBreak` / `NPC` / `Pet` / `Boss` 条目 | ② | 不是玩家 |
| 官方样本 < 30 的阶段 | ⑤ | 分布不成立 |
| 取样窗口之外的历史记录 | ③ | 由官方统计页决定，本程序不干预 |

前三项决定了请求数：只有完整阶段窗口才会发起表格请求。

## 完整算例

以本仓库已生成的输出为例，召唤师在 P2 的分数是怎么来的。

**第一步**，报告里共 14 把有效 pull，其中 8 把完整打完了 P2（第 3、5、7、10 把在 P2 团灭，
按 ① 的第二条规则排除）。这 8 把里该玩家的 rDPS：

```
第4把 5706   第6把 5850   第9把 5991   第11把 5782
第12把 5853  第13把 5757  第14把 6138  第15把 5645
```

**第二步**，升序排列后取中位数（`n = 8` 为偶数，取中间两个的平均）：

```
5645  5706  5757  5782 | 5850  5853  5991  6138
代表值 = (5782 + 5850) / 2 ≈ 5816.24
```

**第三步**，官方 P2 召唤师曲线，样本 350 条：

```
p  0 = 2217.48      p 50 = 6031.95      p 95 = 6535.60
p 10 = 5432.11      p 75 = 6278.00      p 99 = 6645.39
p 25 = 5753.91      p 90 = 6439.50      p100 = 6848.19
```

样本 350 ≥ 30，通过闸门。

**第四步**，代表值落在 p25 与 p50 之间：

```
ratio = (5816.24 − 5753.91) / (6031.95 − 5753.91) = 0.2242
分位  = 25 + (50 − 25) × 0.2242 = 30.6

线性  = 100 × (5816.24 − 2217.48) / (6848.19 − 2217.48) = 77.7

相对中位 = 5816.24 / 6031.95 − 1 = −3.6%
```

这三个数与表格输出的 `30.6 / 77.7 / -3.6%` 完全一致。

**第五步**，该玩家五个有数据的阶段：

```
阶段                     平均时长    分位    官方样本
P1: Adelphel …            166.6s      —          2      ← 被样本闸门挡下
P2: King Thordan          196.4s   30.56        350
P3: Nidhogg               126.9s   35.64        348
P4: The Eyes               74.4s   16.35        351
Intermission: Rewind!      82.5s    6.90        359
```

只有后四个参与加权：

```
总分 = (30.56×196.4 + 35.64×126.9 + 16.35×74.4 + 6.90×82.5) / (196.4+126.9+74.4+82.5)
     = 12310.4 / 480.2
     = 25.6
```

P1 虽然有数据，但官方样本只有 2 条，达不到 30 的闸门，所以计分阶段显示 `4 / 5`。

## 复算入口

明细 CSV（`out/<报告>-<口径>-明细.csv`）是每把每阶段每人一行的原始数值，
汇总 CSV 带着 p0/p25/p50/p75/p95/p100 六个官方锚点与样本量。
这两份文件足以把上面每一步独立复算一遍。
