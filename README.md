# 验尸官 · autopsy

团灭之后把 FF Logs 日志逐 P 剖开，对着官方数据找出是哪一段、哪个人出了问题。

具体做的事：把报告按 P 拆开，再拿每名玩家的成绩去比官方统计里同职业、同一个 P 的记录，
算出他在这一段里究竟排在什么位置。

开荒期的日志几乎全是团灭，没有通关排名可看，整场 DPS 也没有意义——
一把打到 P3 和一把打到 P6 的数字根本没法比。按 P 拆开之后才有一条公平的横轴。

## 它解决的问题

副本统计页给的是每个职业在每个 P 的完整分数分布，本程序做的是把报告里的实测值放到那条分布上：

```
钐镰客   P4: The Eyes   8,751   官方中位 7,832   +11.7%   87.0 分
召唤师   P4: The Eyes   6,774   官方中位 7,241    -6.4%   16.3 分
```

## 依赖

- Node.js 23.6 以上。程序直接运行 `.ts`，不需要编译，也没有任何 npm 依赖。
- 系统自带的 `curl`。Windows 10 1803 以上、macOS 与主流 Linux 都有；装在别处可用
  环境变量 `FFLOGS_CURL` 指定完整路径。
- 仅导出图片时需要：系统上已有的 Chrome、Edge 或 Chromium，用 `FFLOGS_BROWSER` 指定路径亦可。

## 配置

把 `config.example.json` 复制成 `config.json`，填入 FF Logs 的 v1 API key：

```json
{
  "host": "cn.fflogs.com",
  "apiKey": "你的 32 位 key"
}
```

也可以改用环境变量 `FFLOGS_API_KEY` 与 `FFLOGS_HOST`。`config.json` 不进版本库。

## 使用

```bash
node src/main.ts score https://cn.fflogs.com/reports/xxxxxxxxxxxxxxxx
node src/main.ts score xxxxxxxxxxxxxxxx --format console,html,markdown,csv,image
node src/main.ts score xxxxxxxxxxxxxxxx --phase 3 --aggregate best
node src/main.ts baseline --zone 59 --boss 1076
node src/main.ts cache clear
```

`npm link` 一次之后就能直接敲 `autopsy`：

```bash
npm link
autopsy score https://cn.fflogs.com/reports/xxxxxxxxxxxxxxxx
```

| 选项 | 说明 |
| --- | --- |
| `--metric` | `rdps`（默认）、`adps`、`ndps`、`cdps`、`hps` |
| `--fight` | 只评某一把 |
| `--phase` | 只评某个 P |
| `--aggregate` | 同一个 P 打了多把时取 `median`（默认）或 `best` |
| `--window` | 比对官方最近多少天的数据，默认随副本页面 |
| `--format` | `console`、`html`、`markdown`、`csv`、`image`，逗号叠加 |
| `--out` | 文件输出目录，默认 `out` |
| `--width` | 导出图片宽度，默认 1300 |
| `--scale` | 导出图片像素密度，默认 2 |
| `--names` | 显示真实角色名与报告地址，默认匿名 |
| `--refresh` | 忽略本地缓存重新抓取 |
| `--no-color` | 关闭颜色 |

## 输出去哪了

每次运行单独一个文件夹，按**日志自身的时间**命名，一晚上跑好几份也不会混在一起：

```
out/2026-09-20-1907-幻想龙诗绝境战-rdps/
  01-总览.png          02-点评.png
  03-P1.png            04-P2.png
  05-P3.png            06-P4.png
  07-Intermission.png  08-没算分的P.png
  报告.html            报告.md
  汇总.csv             明细.csv
```

用日志时间而不是运行时间，同一份日志重跑会覆盖旧结果，这正是想要的；换个口径算则是另一个
文件夹，因为目录名带着口径。加了 `--names` 时目录名用报告代码，因为那时本来也不打算藏。

## 默认匿名

输出里**不出现角色名、记录者和报告地址**，每个人按职业显示；同队两个同职业时补序号，
不会两行同名。输出目录名也不带报告代码——那串代码本身就等于那条链接。

这样默认是因为这类报告十有八九要发给一群人看，默认把名字亮出来等于默认在点名。
每个人知道自己打的是什么职业，队内该认的还是认得出来。

自己私下核对想看真名，加 `--names`。

## 通关了就有整场成绩

逐 P 拆开是为了给团灭的日志一条公平的横轴。真通关了，整场那个数才是大家最认的，
所以报告里会多出一块「整场」：总评表加一列，矩阵加一列，图片多出一张，点评里也会单独说一句。

整场**不并进逐 P 的总分**——整场本来就是各 P 之和，混在一起等于把同一份成绩数了两遍。

没通关的日志不会出现这一块。

## 两个分数

官方统计的取样窗口**随副本而定**，程序从页面自己读：老本给的是 2 周到 12 周，
光暗未来这类新本只给一天到两周。拿一个副本不提供的天数去问，返回的是一张空表而不是报错，
所以 `--window` 给了不存在的档位会直接报错并列出可选项。

**百分位**是主分：拿本人成绩去比官方统计里同职业、同一个 P 的所有记录，看排在多少名。
配色和 FF Logs 一致，看惯排行榜的人不必重新建立直觉。官方给出 0/10/25/50/75/90/95/99/100
九个锚点，之间线性插值。

**区间分**是 `100 × (实测 − 最低) ÷ (最高 − 最低)`，也就是在官方最低值到最高值之间的位置。
它直观，但最低值往往来自某条开场就倒了的记录，所以只作参考，不当主分。

玩家总评按各 P 的时长加权，一分钟的 P 不会和三分钟的 P 同等权重。

总评里的**算分 P** 写成 `4 / 5`：后者是这名玩家有数据的 P 数，前者是其中真正算进总分的。
被团灭打断、或者官方样本太少的 P 只展示，不参与计算。

## 点评

表格之外还有一段点评，把数字里值得开口说的部分挑出来：全队最吃力的 P、团灭最多的地方、
每个人最薄弱在哪个 P、差到什么程度。每一条结论都把支撑它的那个数写进句子，可以直接回表格核对。

```
观察 全队      全队最吃力的是 P3: Nidhogg，平均 49.3 分，8 个人里有 5 个低于官方中位。
观察 全队      14 把里 P2: King Thordan、P5: King Thordan II 各倒了 5 把，是团灭最多的两个 P。
严重 学者      最薄弱的是 P2: King Thordan，9.4 分，排在同职业最后 10%，比官方中位低 19.6%。
注意 暗黑骑士  P3: Nidhogg 打了 7 把，最好 5,040、最差 3,215，差了 38.3%，中间有几把明显失手。
```

四个程度是 `严重`、`注意`、`观察`、`亮点`。判据与措辞上的克制写在
[docs/算法.md](docs/算法.md) 的第七节。

## HTML 报告

`--format html` 生成一个自包含的单文件，不引用任何外部资源，双击就能开，也能直接发给队友。
版面以**各 P 百分位**的矩阵开头：

```
玩家        P2   P3   P4  Intermission   总评   算分 P
机工士      95   88   21       60        75.6    4/5
龙骑士      34   22   44       26        30.9    4/5
召唤师      31   36   16        7        25.6    4/5
```

同样一组数字，排成几张互不相干的明细表，和排成一张玩家乘 P 的矩阵，读出来的东西完全不同：
一行横着看是某个人在哪个 P 掉了，一列竖着看是全队卡在哪个 P，都不用来回翻。格子的颜色就是分数，
和 FF Logs 一致；鼠标停上去能看到原始数值、官方中位和样本数。

矩阵下面依次是关键数字、点评、各 P 的明细（折叠起来，要核对时再展开，里面带一条从官方最低到
最高的分布轨道）、没算分的 P。全队都没算出分的 P 不占矩阵的列，只在下方注明。

## 导出图片

`--format image` 直接产出一张 PNG，可以扔进群里。

```bash
node src/main.ts score <链接> --format image
node src/main.ts score <链接> --format image --width 1000 --scale 1
```

借系统上已有的 Chrome、Edge 或 Chromium 无头渲染，**不引入任何打包好的浏览器**——那类依赖
动辄几百兆，为了一张图不值得。找不到浏览器时会明确报错，可以用环境变量 `FFLOGS_BROWSER`
指定完整路径。

**不是一张长图，是拆开的几张小图**：总览、点评、每个 P、没算分的 P，各出一张。整份报告摊平
接近一万像素高，扔进群里没人看得下去；拆开之后每张都是能一眼看完的大小，想聊哪个 P 就发哪一张。
每张自带一行说明自己出自哪份日志、按什么口径算，单独发出去也不会不知所云。

网页里各 P 的明细是折叠的，点一下就展开；图片点不动，所以一律摊开。

高度按内容自动裁切：页面渲染完会把自己的 `scrollHeight` 写进 DOM，用 `--dump-dom` 读回来，
再按这个高度截一次，图片底部不会拖一片空白。

默认 1300 宽、像素密度 2。以八人五个 P 的报告为例，一张 P 图是 2600 × 958、约 160 KB，
总览 2600 × 1614、约 250 KB。嫌大就 `--scale 1`。

## 三条它不会骗人的地方

**被团灭打断的 P 不算分。** 官方数据取自通关记录，每个 P 都是完整打完的；拿一个打了 66 秒就团灭的
P5 去和完整的 P5 比，结果只会好看而没意义。这类 P 仍会单独列出，但不参与任何分数。

**官方样本少于 30 条的 P 不算分。** 极少有队伍从 P1 开始打，第一个 P 的官方记录常常只有个位数，
拿两三条记录当参照，谁都是满分。这类 P 显示为“样本不足”。

**数值口径与官方逐位一致。** 每秒数值的除数是 `combatTime` 而非窗口长度。用它复算国服龙骑榜首的
通关成绩，得到 7972.33690838507，官方公布值是 7972.3369083851，差在 1e-11 量级。
这条有回归测试守着。

## 请求成本

一份完整报告的冷启动约 **49 次请求**：统计页 21 次（1 次页面加 5 个 P 各 4 个数据集），
v1 接口 28 次（1 次战斗列表加 27 个 P 的时间窗）。所有响应都落磁盘缓存，重跑同一份报告是零请求。
官方数据按 P 惰性补齐，同一副本换一份报告通常只需报告那一侧的请求。

程序对两个数据源都做了节流，v1 接口会读取响应头里的配额并在结束时报出剩余量。

## 结构

```
src/
  core/      配置、错误、领域类型、终端原语
  net/       v1 接口客户端、统计页数据源与其纯函数解析、HTTP 传输、磁盘缓存
  domain/    P 的切分、数值换算、官方数据与百分位插值、评分
  render/    控制台、HTML、Markdown、CSV、图片导出
```

`net/http.ts` 走系统 curl 而不是 Node 内置的 fetch 或 http2，原因写在该文件的注释里：
站点前置的防护按 TLS 握手指纹判断来路，Node 自带的 OpenSSL 指纹在统计页那条路径上一律被挡。
同一处还有另一个实测结论——请求头名写成小写 `accept` 会被判成机器人，写成 `Accept` 才正常。

node --test src/
